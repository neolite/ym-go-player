# Легковесный плеер Яндекс Музыки — дизайн

> Дата: 2026-08-21
> Исследование-основание: [`docs/research/custom-yandex-music-player.md`](../../research/custom-yandex-music-player.md)
> Статус: утверждён к реализации

---

## 1. Цель

Заменить официальный десктоп-клиент Яндекс Музыки на собственный — лёгкий, без промо-блоков, с предсказуемым поведением.

Что не устраивает в официальном (со слов заказчика):
- Electron на 100+ МБ, ест ОЗУ и батарею;
- лишний UI: подкасты, шортсы, баннеры, навязанные подборки;
- отсутствуют нужные фичи;
- хочется устойчивого воспроизведения при плохой сети.

**Критерий успеха v1:** бинарь единицами–десятками мегабайт запускается за доли секунды, играет «Мою волну» и личные плейлисты, переживает просадку сети, не показывает ни одного промо-элемента.

## 2. Границы

**В скоупе v1**
- Авторизация по OAuth-токену Яндекса.
- «Моя волна» (ротор) — основной сценарий прослушивания. **Допущение автора спеки, ждёт подтверждения** (см. §13).
- Личные плейлисты и «Мне нравится».
- Поиск по трекам, альбомам, артистам.
- Воспроизведение: play/pause/next/prev/seek, громкость, очередь.
- Лайк/дизлайк текущего трека.
- Отправка фидбека прослушивания — чтобы рекомендации продолжали учиться.
- Транзитный буфер воспроизведения (см. §5.3).
- Медиа-клавиши и карточка «сейчас играет» в ОС.

**Явно вне скоупа**
- **Выгрузка каталога в постоянные файлы.** Плеер не сохраняет музыку за пределы сессии. Буфер §5.3 ограничен по объёму, привязан к текущей очереди и очищается при выходе. Постоянная офлайн-библиотека — задача официального приложения, где офлайн входит в Плюс.
- **Расшифровка зашифрованных lossless-потоков.** Если качество отдаётся под защитой, оно не поддерживается; плеер берёт лучшее из доступного в открытом виде.
- Last.fm-скробблинг — не нужен. Подтверждено заказчиком 2026-08-21.
- Ynison (синхронизация с официальным приложением, роль «пульта») — для самостоятельного плеера не требуется.
- Подкасты, шортсы, соцфичи, редакционные подборки.

**Предусловие:** активная подписка Плюс. Без неё API отдаёт только 30-секундные превью, и плеер не имеет смысла. Отсутствие Плюса детектируется на старте и сообщается явно.

## 3. Архитектура

Go-демон держит всю логику и отдаёт локальный HTTP; UI — веб-страница, вшитая в тот же бинарь через `//go:embed`. Аудио декодирует браузер.

```
┌───────────────────────────────────────────────┐
│ Frontend — HTML + vanilla TS, без фреймворка   │
│ <audio> декодирует MP3 / AAC / FLAC нативно    │
└───────────────────┬───────────────────────────┘
                    │ HTTP + SSE, 127.0.0.1
┌───────────────────▼───────────────────────────┐
│ Go-демон, один бинарь                         │
│  ├─ ymapi/    клиент неофициального API        │
│  │    ├─ sign.go     подписи (md5 / hmac)      │
│  │    └─ *.go        эндпоинты, DTO            │
│  ├─ player/   конечный автомат очереди         │
│  ├─ rotor/    «Моя волна»: батчи + фидбек      │
│  ├─ stream/   аудио-прокси и буфер             │
│  ├─ auth/     токен в системном keychain       │
│  └─ httpapi/  транспорт, SSE, статика          │
└───────────────────────────────────────────────┘
```

**Обоснование стека.** Go выбран вместо Rust/Tauri: вся криптография задачи (`md5`, `hmac`, `sha256`, `base64`) есть в стандартной библиотеке, поэтому порт протокола не тянет ни одной зависимости, а вычислительной нагрузки, оправдывающей Rust, здесь нет. Веб-UI вместо нативного выбран потому, что снимает необходимость тащить в Go аудиодекодеры и работу со звуковой картой — `<audio>` умеет все нужные форматы.

**Путь развития.** Поскольку граница «демон отдаёт HTTP» зафиксирована, обёртывание в нативное окно (Wails — аналог Tauri для Go) позже не потребует изменений в логике. Это станет актуально, если понадобятся произвольные глобальные хоткеи, недоступные вкладке браузера.

## 4. Модули и контракты

| Модуль | Задача | Знает о | Тестируется |
|---|---|---|---|
| `ymapi` | HTTP-клиент Яндекса, подписи, DTO | только о протоколе | фикстуры через `httptest` |
| `player` | очередь, текущая позиция, состояние | о треках как о данных | чистые unit-тесты |
| `rotor` | подкачка волны, фидбек ротора | `ymapi` | фикстуры |
| `stream` | резолв ссылок, проксирование, буфер | `ymapi` | unit + фикстуры |
| `auth` | хранение и валидация токена | keychain ОС | unit с фейковым хранилищем |
| `httpapi` | REST, SSE, отдача статики | всё выше | интеграционные |

Жёсткое правило: **`player` не делает сетевых вызовов**, а `ymapi` ничего не знает о существовании плеера. Это то, что делает оба модуля тестируемыми без сети и позволяет менять UI, не трогая логику.

## 5. Ключевые механизмы

### 5.1 Подписи ссылок

Две схемы, обе портируются на стандартную библиотеку Go:

- **Старая (MP3/AAC).** `download-info` возвращает XML с полями `host`, `path`, `ts`, `s`. Подпись — `md5(соль + path[1:] + s)`, итоговый URL собирается как `https://{host}/get-mp3/{sign}/{ts}{path}`. Схема подтверждена по исходнику библиотеки MarshalX.
- **Новая (высокое качество и FLAC).** Эндпоинт `get-file-info` с подписью HMAC-SHA256 и base64 без padding. Детали **не подтверждены первичным источником**. Это не фундамент, а расширение: реализуется отдельным шагом после того, как заработает старая схема, и с явным условием остановки — см. §11 и §2.

  **Условие остановки.** Если в ходе проверки окажется, что высокое качество отдаётся под технической защитой, работа по этому шагу прекращается. Плеер играет лучшее из доступного в открытом виде; обход защиты не реализуется ни при каких условиях (§2).

Константы и порядок полей берутся из протокола как факты. Исходный код LGPL-библиотеки **не переносится построчно**: пишем свою реализацию, сверяясь с поведением протокола, а не копируя выражение.

### 5.2 Аудио-прокси

Фронтенд никогда не получает прямую ссылку Яндекса. Он запрашивает `GET /stream/{trackId}`, демон в этот момент резолвит свежую подписанную ссылку и переливает байты, проксируя заголовки `Range`.

Три причины, почему прокси, а не редирект:

1. **TTL.** Подписанная ссылка живёт около минуты, дальше отдаёт 410. При редиректе пауза дольше минуты или перемотка в длинном треке ломали бы поток необъяснимым для пользователя образом. Прокси перерезолвит прозрачно.
2. **Токен не покидает процесс демона** и не появляется в JS.
3. **Перемотка.** `<audio>` реализует seek через `Range`-запросы; проксируя их, получаем корректный seek и естественную точку, где живёт буфер.

### 5.3 Буфер воспроизведения

Транзитный, ограниченный, привязанный к очереди:

- основное правило: держит **текущий трек и один следующий**, не больше;
- страховочный предел на случай аномально больших файлов — 256 МБ суммарно, при превышении вытесняется самое старое;
- живёт только в рамках сессии, полностью удаляется при выходе;
- не индексируется, не имеет UI для просмотра, не экспортируется.

Назначение — сгладить просадки сети и обеспечить мгновенный переход к следующему треку. Это техническая необходимость плеера, а не хранилище: TTL ссылки в минуту делает воспроизведение без упреждающей подкачки заикающимся.

### 5.4 «Моя волна»

Ротор отдаёт треки батчами. Демон запрашивает следующий батч, когда в очереди остаётся менее двух треков, передавая идентификаторы уже проигранного.

**Два независимых канала фидбека, оба обязательны:**
- общий фидбек прослушивания — питает статистику и рекомендации аккаунта;
- фидбек ротора (старт радио, старт трека, завершение, скип) — обучает саму волну.

Без них волна деградирует, и плеер превращается в проигрыватель случайного. Это то, что отличает клиент от загрузчика.

## 6. Аутентификация

Своё OAuth-приложение у Яндекс Музыки создать нельзя, поэтому используется implicit-схема с client_id официального клиента: демон открывает браузер на странице Яндекса, пользователь логинится там же, токен забирается из фрагмента URL после редиректа.

- Логин происходит **на стороне Яндекса** — мы не видим пароль и не упираемся в SmartCaptcha, ломающую программный вход по паролю.
- Токен живёт около года; автообновления нет — при истечении UI показывает экран входа.
- Хранение — **системный keychain**, не файл в домашней директории.
- На старте вызывается статус аккаунта: проверяются валидность токена, наличие Плюса и регион.

## 7. Состояние

Единственный источник правды о воспроизведении — структура в памяти демона:

```
PlayerState {
  status:     idle | loading | playing | paused | error
  track:      Track | null
  position:   секунды
  duration:   секунды
  volume:     0..1
  queue:      []Track
  queueIndex: int
  source:     wave | playlist | search | likes
  error:      string | null
}
```

Фронтенд подписан на изменения через SSE и сам состояния не хранит — только рисует. Практическое следствие: перезагрузка вкладки не прерывает музыку, UI просто переподключается к живому состоянию.

## 8. HTTP API демона

Всё на `127.0.0.1`, порт выбирается свободный и печатается при запуске.

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/api/events` | SSE-поток `PlayerState` |
| `GET` | `/api/auth/status` | валидность токена, Плюс, регион |
| `POST` | `/api/auth/login` | запустить OAuth-флоу |
| `POST` | `/api/auth/logout` | стереть токен из keychain |
| `GET` | `/api/search` | поиск: `q`, `type` |
| `GET` | `/api/playlists` | список плейлистов пользователя |
| `GET` | `/api/playlists/{kind}` | содержимое плейлиста |
| `GET` | `/api/likes` | «Мне нравится» |
| `POST` | `/api/play` | начать источник: волна / плейлист / поиск |
| `POST` | `/api/player/{pause,resume,next,prev}` | управление |
| `POST` | `/api/player/seek` | перемотка |
| `POST` | `/api/player/volume` | громкость |
| `POST` | `/api/tracks/{id}/like` | лайк |
| `DELETE` | `/api/tracks/{id}/like` | снять лайк |
| `POST` | `/api/tracks/{id}/dislike` | дизлайк, влияет на волну |
| `GET` | `/stream/{trackId}` | аудио-прокси с поддержкой `Range` |
| `GET` | `/` | вшитый фронтенд |

## 9. Фронтенд

Vanilla TypeScript, собранный esbuild, вшитый в бинарь через `//go:embed`. Никакого React — задача не оправдывает рантайм фреймворка, а состояние и так живёт на сервере.

Три экрана: **сейчас играет** (обложка, название, прогресс, управление, лайк), **библиотека** (плейлисты и «Мне нравится»), **поиск**. Никаких промо-блоков, подборок и рекламных мест — это прямое требование.

Медиа-клавиши и системная карточка «сейчас играет» — через **MediaSession API**. Это даёт play/pause/next с клавиатуры и наушников, а также обложку в центре управления ОС. Настоящие произвольные глобальные хоткеи вкладке недоступны — при необходимости это триггер перехода на Wails (§3).

## 10. Обработка ошибок

| Ситуация | Поведение |
|---|---|
| Токен невалиден или истёк | Экран входа, не пустая страница |
| Нет подписки Плюс | Явное сообщение на старте, а не «загадочно не играет» |
| Ссылка отдала 410 | Молча перезапросить один раз, затем пометить трек ошибочным и идти дальше |
| Трек недоступен в регионе | Скип со сноской в UI, очередь продолжается |
| Сеть пропала | Пауза с индикатором, доигрываем из буфера, ретраи с экспоненциальным откатом |
| Ротор не отдал батч | Доигрываем очередь, показываем предупреждение, ретрай |
| Порт занят | Берём следующий свободный |

Общий принцип: **плеер не падает и не молчит.** Любая ошибка либо восстанавливается сама, либо объясняется пользователю словами.

## 11. Тестирование

- **Подписи — golden-тесты** с фиксированными векторами. Это единственное место, где ошибка молча даёт 403 вместо музыки, поэтому проверяется побайтово.
- **`ymapi`** — против записанных ответов через `httptest`, без сети.
- **`player`** — чистые unit-тесты автомата: границы очереди, next на последнем треке, skip при ошибке.
- **`stream`** — корректность `Range`, поведение при 410, границы вытеснения буфера.
- **Живой смоук** — отдельно, за build-тегом, требует реальный токен; в CI не гоняется.

**Порядок валидации рисков.** Работа начинается с шагающего скелета: токен → метаданные одного трека → подписанная ссылка → байты играют в браузере.

Скелет строится **на старой MP3/AAC-схеме**, а не на `get-file-info`. Причина принципиальная: старая схема подтверждена первичным источником — исходником `download_info.py`, солью подписи и минутным TTL, — и её достаточно, чтобы доказать всю цепочку целиком. Ставить в фундамент единственное непроверенное звено значило бы смешивать две ошибки: «мы неправильно собрали цепочку» и «мы неправильно угадали подпись», — и не иметь возможности их различить.

`get-file-info` проверяется **отдельным поздним шагом**, когда воспроизведение уже работает. Если он не заведётся или упрётся в защиту — плеер остаётся полностью рабочим на проверенном пути, просто без lossless.

## 12. Риски

| Риск | Вероятность | Реакция |
|---|---|---|
| Подпись `get-file-info` устроена иначе | Высокая | Не в фундаменте: базовый путь на проверенной MP3-схеме, lossless — отдельный поздний шаг, при провале просто не реализуется |
| Яндекс меняет протокол | Средняя, постоянная | Изоляция в `ymapi`; ломается один модуль, а не приложение |
| Высокие качества отдаются под защитой | Средняя | Играем лучшее доступное в открытом виде; не обходим защиту |
| Токен отзывают за сторонний клиент | Низкая, эмпирически не подтверждена | Понятный экран перелогина |
| Официального API нет и не будет | Данность | Принято осознанно; ToS-риск на стороне пользователя |

## 13. Открытые вопросы

| Вопрос | Текущее допущение | Почему важно |
|---|---|---|
| Нужна ли «Моя волна» в v1? | **Да** — заложена как основной сценарий | Это самый крупный кусок v1: модуль `rotor`, второй канал фидбека, логика подкачки батчами. Если волна не нужна, объём v1 заметно падает. Ответ заказчика на этот вопрос был получен в искажённой раскладке и надёжно расшифрован **только в части Last.fm**, поэтому волна остаётся допущением автора спеки. |

## 14. После v1

Кандидаты, сознательно отложенные: нативное окно на Wails с глобальными хоткеями; альбомы и страницы артистов; тексты песен; эквалайзер; горячие клавиши внутри страницы; тёмная и светлая темы.

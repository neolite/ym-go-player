# Навигация по артистам и альбомам — дизайн

> Дата: 2026-08-24
> Основание: [`docs/superpowers/specs/2026-08-21-yandex-music-lightweight-player-design.md`](2026-08-21-yandex-music-lightweight-player-design.md)
> Статус: ждёт ревью пользователя

---

## 1. Цель

Клик по имени артиста или названию альбома открывает карточку с плоским списком его треков, не прерывая текущее воспроизведение. Клик по треку внутри карточки заменяет очередь и играет с этого трека — так же, как уже работает клик по плейлисту.

Второй заход этой же сессии — тексты треков (lyrics) — вынесен в отдельную последующую спеку: другая область API (нужна HMAC-подпись), другой UI-паттерн (панель, а не список).

## 2. Границы

**В скоупе**
- Карточка артиста: плоский список его треков.
- Карточка альбома: плоский список его треков (без деления на «диски» в UI — Yandex может вернуть альбом несколькими «volumes», сводим в один список).
- Имя артиста кликабельно везде, где сейчас рисуется строка трека: в очереди (`#list`), в карточке плейлиста/лайков (тот же рендер), в шапке текущего трека.
- Название альбома кликабельно в шапке текущего трека (там же, где появится сама надпись — сейчас альбом в шапке не показан вообще).
- Один трек может нести несколько артистов — кликабелен каждый по отдельности.

**Явно вне скоупа**
- Полноценный дрилл-даун со своими страницами и «назад» (артист → его альбомы → альбом → треки). Пользователь явно выбрал плоский вариант.
- Отдельный экран результатов поиска — его в приложении нет вообще (поиск сразу подставляет треки в `#list`), заводить его ради этой фичи не нужно.
- Информация об артисте/альбоме (фото, биография, год выпуска и т.д.) — только список треков.
- Пагинация/«показать ещё» внутри карточки — берём один разумный по размеру запрос (см. §4), не собираем весь каталог артиста.
- Тексты треков (lyrics) — следующая спека.

## 3. Откуда взялись факты об API

Раздел 1 фонового ресёрча (форк этой сессии) прочитал исходники `MarshalX/yandex-music-api` — той же эталонной библиотеки, на которую уже опирается весь проект (см. `docs/research/custom-yandex-music-player.md`). Это даёт статус **✅ по исходнику**, но не «живым прогоном»: реального HTTP-запроса к API с этими путями ещё не было. Живая проверка произойдёт естественным образом на этапе реализации — так же, как до сих пор проверялись все остальные эндпоинты этого проекта.

- Треки артиста: `GET /artists/{artistId}/tracks?page=0&page-size=N` → `{tracks: [...], pager: {...}}`.
- Треки альбома: `GET /albums/{albumId}/with-tracks` → объект альбома с полем `volumes: [][]Track` (треки разбиты по «дискам», в разных volumes может быть разное число треков).
- Оба вложенных объекта (`artists[]`, `albums[]`) внутри обычного трека уже несут `id` в сыром JSON — рядом с уже читаемыми `name`/`title`.

## 4. Модель данных

`internal/player/state.go`, структура `Track` — два новых поля рядом с уже существующими, без переделки `Artists []string`/`Album string` в структуры `{id, name}`:

```go
type Track struct {
    ID         string   `json:"id"`
    Title      string   `json:"title"`
    Artists    []string `json:"artists"`
    ArtistIDs  []string `json:"artistIds"`  // новое, тот же порядок и длина, что Artists
    Album      string   `json:"album"`
    AlbumID    string   `json:"albumId"`    // новое, пусто если у трека нет альбома
    CoverURL   string   `json:"coverUrl"`
    Duration   int      `json:"duration"`
    Available  bool     `json:"available"`
    Liked      bool     `json:"liked"`
}
```

`internal/ymapi/types.go`, `apiTrack.toPlayer()` — параллельно циклу по `Artists` собираем `ArtistIDs` из уже присутствующего в JSON `artists[].id`; `AlbumID` — из `albums[0].id`, тем же способом, каким сейчас берётся `albums[0].title`.

**Почему точечная добавка, а не структура `{id, name}`:** переделка `Artists []string` во что-то вроде `[]Artist` — более «правильная» с точки зрения типов, но ломает контракт `Track.artists` для фронтенда (сейчас это простой массив строк, использован в нескольких местах — заголовок, строки очереди, MediaSession) ради поля, которое нужно только для клика. Два параллельных массива дешевле по риску регрессии и оставляют существующий код нетронутым.

## 5. Бэкенд

**`internal/ymapi/artists.go`** (новый файл) — `ArtistTracks(ctx, artistID string) ([]player.Track, error)`. Один запрос с фиксированным `page-size` (например 100 — «разумная карточка», не весь каталог), без пагинации на нашей стороне: с точки зрения §2 «без показать ещё» первая страница и есть весь ответ.

**`internal/ymapi/albums.go`** (новый файл) — `AlbumTracks(ctx, albumID string) ([]player.Track, error)`. Разворачивает `volumes: [][]Track` в плоский `[]player.Track` (`for _, vol := range volumes { for _, t := range vol { ... } }`), порядок дисков и треков внутри диска сохраняется.

**`internal/httpapi/routes.go`** — два новых маршрута, по образцу `handleSearch`/`handleLikes` (публичный каталог, без `requireUID` — это не про библиотеку пользователя):

```go
mux.HandleFunc("GET /api/artists/{artistId}/tracks", a.handleArtistTracks)
mux.HandleFunc("GET /api/albums/{albumId}/tracks", a.handleAlbumTracks)
```

Оба хендлера — тонкая обёртка (`client(w)` → вызов ymapi-метода → `apiError`/`writeJSON`), без изменения состояния плеера. `handlePlay` трогать не нужно вообще: клик по треку внутри карточки идёт через уже существующий `POST /api/play {"source":"tracks","tracks":[...]}` — фронтенд сам вырезает список от кликнутого трека до конца списка карточки перед отправкой (тот же порядок, что был в карточке, продолжится дальше).

Имя/название для заголовка карточки бэкенду возвращать не нужно — фронтенд уже знает его локально (это тот текст, по которому кликнули), отдельного «инфо об артисте» эндпоинта не заводим.

## 6. Фронтенд

**Рендер строки трека** (`web/src/app.ts`, сейчас один такой код в `render()` для `#list`) — вместо `artistEl.textContent = " — " + track.artists.join(", ")` — по одному `<span class="artistLink">` на артиста с обработчиком клика, разделённые текстовыми узлами `", "`. Название альбома в шапке текущего трека сейчас не выводится вообще — добавляется новая строка под `#artist`, кликабельная так же.

**Открытие карточки** — по образцу `btnLists`: запрос `GET /api/artists/{id}/tracks` (или albums), рендер в существующий `#lists` (переключение `#list`/`#lists` уже есть, доп. UI не заводим), заголовок карточки — имя/название, взятое из клика, плюс кнопка «✕ назад» → `showQueue()`.

**Клик по треку внутри карточки** — `POST /api/play {"source":"tracks","tracks": cardTracks.slice(clickedIndex)}`, затем `showQueue()` — тот же паттерн, что уже есть у клика по плейлисту.

**`interface Track`** (`web/src/app.ts`) — добавляются `artistIds: string[]` и `albumId: string`, зеркально бэкенду.

## 7. Обработка ошибок

- Запрос карточки не удался (сеть, 404 несуществующего ID) — `showTransientError`, карточка не открывается, текущий вид (`#list`) остаётся как был. Тот же паттерн, что уже есть в обработчике `btnLists`.
- Трек без альбома (`AlbumID == ""`) — строка альбома в шапке не рендерится вовсе (аналогично тому, как сейчас скрывается обложка при пустом `coverUrl`).
- Трек с одним артистом без `id` (не должно происходить по документированной форме API, но JSON внешний) — такое имя рендерится как обычный текст без клика, не ломая остальную строку.

## 8. Тестирование

Бэкенд — TDD, как и весь Go-код проекта:
- `internal/ymapi/artists_test.go` — httptest-сервер отдаёт фикстуру `{tracks:[...], pager:{...}}`, проверяем путь запроса и что список треков распарсен (включая новый `ArtistIDs`/`AlbumID` на распарсенных треках).
- `internal/ymapi/albums_test.go` — фикстура с двумя `volumes`, проверяем, что результат — плоский список в правильном порядке.
- `internal/httpapi` — тонкий тест на каждый новый маршрут (по образцу существующих тестов `handleSearch`/`handleLikes`): моковый бэкенд отдаёт фикстуру, хендлер отвечает 200 с тем же списком.

Фронтенд — без автоматических тестов (установившийся для этой сессии паттерн: `tsc --noEmit` + `npm run build` + ручная проверка в браузере через claude-in-chrome). План ручной проверки: клик по артисту в очереди → карточка со списком → клик по треку → очередь заменилась, играет с выбранного; то же для альбома из шапки; клик «✕ назад» без выбора трека — воспроизведение не прерывалось.

## 9. Открытые вопросы

Нет — все развилки закрыты в диалоге при брейншторминге (плоский список без альбомов внутри карточки артиста; клик по треку заменяет очередь; кликабельность имени артиста — везде, где рисуется трек, не только в шапке/поиске).

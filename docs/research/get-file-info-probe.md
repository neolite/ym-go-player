# Проба схемы `get-file-info` (задача 14, шаг 5)

**Статус: НЕ ВЫПОЛНЕНО.** Этот файл — заготовка, а не отчёт о результате.
Исполнитель задачи 14 не располагает настоящим OAuth-токеном с активной
подпиской Плюс и не может отправить ни одного запроса к боевому API.
Каждое поле ниже, помеченное `[ЗАПОЛНЯЕТ ВЛАДЕЛЕЦ УЧЁТНОЙ ЗАПИСИ]`,
не содержит и не должно содержать угаданного или правдоподобного значения —
пустое честно помеченное место лучше вымышленного числа.

## Условие остановки

Цель пробы — единственная: выяснить, отдаёт ли эндпоинт `get-file-info`
высокое качество (или FLAC) **в открытом виде**, то есть в виде прямой
ссылки, которую можно скачать без дополнительного шага расшифровки.

- Если ответ приходит **без** технической защиты контента — шаг закрыт
  положительно, а дальнейшая интеграция `get-file-info` в `ymapi` —
  предмет отдельной задачи, не этой.
- Если ответ приходит **под** технической защитой (шифрование файла,
  DRM-обёртка или что-либо, требующее отдельного шага расшифровки перед
  воспроизведением) — шаг закрывается с **отрицательным результатом**.
  Обход защиты не реализуется ни в коде, ни в виде инструкции в этом
  файле — ни в каком виде. Плеер к этому моменту уже полностью работает
  на проверенной схеме (`download-info` + `get-mp3`, задача 6), так что
  отрицательный результат не блокирует воспроизведение — он лишь
  означает, что высокое качество/FLAC остаются вне скоупа v1.

Это условие действует **безусловно**: даже если ответ окажется
частично открытым (например, метаданные открыты, а сам файл — нет),
пункт «обход не реализуется» распространяется на любую находку,
которая по факту требует обхода защиты контента.

## Что нужно проверить (по §3.2 и §5.1 исследования, `docs/research/custom-yandex-music-player.md:119-127,214`)

Согласно найденным (но **не проверенным по исходнику**, статус ⚠️)
данным:

- Эндпоинт: `get-file-info`.
- Подпись: HMAC-SHA256.
- Подписываемые данные (предполагаемый порядок полей, ⚠️ не проверено
  построчно по исходнику): `Timestamp + TrackID + Quality + Codec +
  Transport`.
- Ключ HMAC (предполагаемый, ⚠️ не проверено): `7tvSmFbyf5hJnIHhCimDDD`.
- Результат подписи — base64 без padding (символы `=` убираются).
- Значения `Quality`, по данным `llistochek`: `0` — AAC 64 kbps,
  `1` — AAC 192 kbps, `2` — FLAC (lossless).

Проба должна подтвердить или опровергнуть эти пункты эмпирически —
именно поэтому она нужна отдельно от уже реализованной и протестированной
схемы `download-info`/`get-mp3`.

## Запрос, который нужно отправить

`[ЗАПОЛНЯЕТ ВЛАДЕЛЕЦ УЧЁТНОЙ ЗАПИСИ]`

Место для точного HTTP-запроса (метод, URL, заголовки, тело/параметры),
которым владелец учётной записи фактически обратился к `get-file-info`.
Указать здесь ровно то, что было отправлено, включая версию подписи,
если она вычислялась вручную для пробы.

```
[ЗАПОЛНЯЕТ ВЛАДЕЛЕЦ УЧЁТНОЙ ЗАПИСИ — точный запрос]
```

## Ответ API

`[ЗАПОЛНЯЕТ ВЛАДЕЛЕЦ УЧЁТНОЙ ЗАПИСИ]`

Место для фактического ответа: код статуса, тело (с вымаранным токеном
и любыми подписанными ссылками на хранилище — они не должны попадать ни
в этот файл, ни куда-либо ещё за пределы процесса демона), заголовки,
имеющие отношение к делу.

```
[ЗАПОЛНЯЕТ ВЛАДЕЛЕЦ УЧЁТНОЙ ЗАПИСИ — точный ответ, без подписанных ссылок и токена]
```

## Вывод: реализуемо ли высокое качество в открытом виде

`[ЗАПОЛНЯЕТ ВЛАДЕЛЕЦ УЧЁТНОЙ ЗАПИСИ]`

Выбрать один из двух вариантов и оставить только его:

- **Положительный результат.** Ответ `get-file-info` отдаёт ссылку на
  файл без технической защиты — интеграция в `ymapi` возможна отдельной
  задачей.
- **Отрицательный результат.** Ответ приходит под технической защитой
  контента (шифрование/DRM/иной обязательный шаг расшифровки) — шаг
  закрыт, обход не реализуется. Плеер продолжает работать на схеме
  `download-info`/`get-mp3`, реализованной и протестированной в задаче 6.
